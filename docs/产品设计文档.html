0.1 产品一句话

把「一句话题材 → 可投放的竖屏短剧成片」做成一条可复现、可审、可批的流水线。 创作侧只做三件事：说题材、挑定妆图、拍板镜头与交付； 其余（写剧本、补台词、出图、出镜、拼接、烧字幕、配音、响度、自检、发布包）由 agent 与代码完成。

0.2 三个组件

组件是什么承担不该做
pi-agentagent 内核（本机 pi + 自有 skill）写剧本、补台词、逐镜审片结论、触发阶段、给出审批的客观门禁不碰 GPU、不碰凭据、不自造状态
ComfyUI渲染执行体（:8188）Z-Image 出定妆图/关键帧，MiniMax-H3 W4A8 出镜不做后期、不存业务状态
Web 平台自定义 Web（审片台 :8095）任务看板 / 审片 / 放映 / 交付审批 / 上传包不执行 GPU 与 ffmpeg 动作，只做投影与触发

0.3 三条产品原则

① 文件即状态。job 目录是唯一真相源；看板、审批、上传包都是它的投影。 不引数据库 = 不会有"看板和目录打架"这类 bug。
② 浏览器是唯一操作面，agent 是唯一执行内核。网页不实现 GPU 逻辑，纪律只有一份。
③ 先便宜后昂贵。10 秒能发现的错（lint、关键帧、证据表）绝不放到 210 秒后（重渲）。

1 · 产品定义

1.1 要解决的问题

没有平台时代价平台怎么解
写剧本、补台词、改一句话，都要手工改一堆文件改一个错别字半小时，改一句台词要重跑整条链阶段化 + 断点续跑：改文本只重跑 shots→assemble→qc（秒级 + 1.5 分钟），不用重渲
出图后才发现构图不对一镜 210 秒的 GPU 白烧关键帧先行（10 s/镜）→ 关键帧拼图一屏审片 → 确认后才烧 GPU
审片要来回传文件一轮审片半天，结论还丢Web 审片台（局域网手机可看）+ 结论落文件 + 文字审核单降级
"文件都在"≠"可以发"空模板审片单、中途态质检报告混过去交付审批层：批准那一刻重跑客观门禁，不过就批不出去
不知道进度，等得心慌反复问、反复重启心跳日志 + 看板投影；状态从目录推断，不猜

1.2 目标用户与场景

独立短剧创作者

1 人 · 有题材有想法 · 没有 GPU 集群 · 没有剪辑团队
场景：给一句话题材，周末产出一集 3 分钟竖屏，投到抖音/红果看数据。 痛点：不懂管线、每个环节都要人守着；产品价值：一个网页 + 三个决策点，其余自动。

小团队工作室（2–5 人）

编剧 / 导演 / 发行分工 · 需要审片留痕
场景：一部三集短剧，编剧定剧本、导演审镜、发行管发布包。 痛点：审片结论散在群里、谁批的说不清；产品价值：审批层留痕（谁、何时、依据、驳回理由），发布包一键交接。

内容运营 / 发行

要的是可投放的物料，不是工程
场景：拿到成片 + 封面 + 标题简介标签 + 质检报告 → 传平台后台 → 看数据。 痛点：不知道能不能发；产品价值：上传包的 CHECKS.md 就是"能不能发"的客观答案。

1.3 价值主张（量化）

指标手工方式平台来源
改一句台词的代价重跑全链（小时级）shots(秒) + assemble(1.5min)实测
发现一镜构图错的代价渲完才发现 = 210 s关键帧 = 10 s实测

1.4 边界：明确不做什么

  • 不做自动发布（抖音/快手/红果）。账号、实名、版权声明、频控风控都不该进脚本 → 只出"上传包 + 文案 + 自检"，人工粘贴。
  • 不做多租户 / 账号体系 / 数据库。单机单人产线；一个服务实例 = 一个剧集根目录。
  • 不做角色 LoRA 训练。一致性靠定妆图 + ref2va（实测 r=0.998）。
  • 不做 TTS 训练。用现成小模型本地合成（单音色/每角色一个音色），情绪表演靠字幕与镜头语言。
  • 不换视频底模。本机只在 MiniMax-H3 W4A8 上验证过加速路线，换底模等于从头踩 sm_75 的量化坑。
  • 不追求真人写实。H3 出的是漫剧/动画风；这是产品形态选择，不是待办项。

2.2 形态原则（为什么这么设计）

文件即状态

job 目录 = 剧本 + 分镜 + clips + 成片 + 审片结论 + 审批决议 + 报告。 状态从文件推断（"clips 数量 = shots 数量 = 已出镜"），不维护第二份状态表。

网页不执行 GPU

网页只做两件事：读文件（投影）、点按钮（起子进程）。 档位、显存门控、关键帧先行这些纪律只写在代码里一份。

两种执行者

cli：本地命令跑确定性阶段（出图/出镜/拼接/质检）。 agent：起 pi 无头 session，把阶段任务卡当提示词交给 agent（内容决策类）。

降级路径同权

没有浏览器 → TUI + 文字审核单 + 证据表；没有网络 → 终端看板； 没有 GPU → 只出文案与剧本。

3 · 端到端工作流

3.1 全景

建任务→ 剧本→ 台词/字幕→ 人物/场景图→ 挑图→ 分镜+关键帧→ 审关键帧→ 分段镜头→ 审成片→ 整集（后期）→ 质检→ 交付审批→ 上传包

紫色 = 人的决策点（3 个）；其余 = agent 与代码。

3.2 阶段规格（13 张看板卡片）

卡片谁做输入产出验收失败处置
T0 写剧本agent题材 + 分集大纲story.json（中英双轨 + 每镜 ref）lint 无 block带错误重试 ≤2 次；仍失败人工改 JSON
T1 剧本预检codestory.json预检报告prompt_en 非空且无中文 / idx 连续 / 角色引用存在秒级挡下毁集级错误
T2 台词/字幕agentstory.json每镜 dialogue_cn / subtitle_cn / voice_cn有效字幕覆盖 ≥ 40%只改文本 → 不用重渲
T3 定妆候选图code(GPU)角色身份锚点cast/<id>_cand*.png脸型/性别/年龄与设定一致重出候选
T3 挑图落地人候选图cast/<id>.png + _alt.png每角色有主图与备图重出候选
T4 分镜codestory.jsonshots.json（H3 固定句式 + 字幕）每镜带 ref 与 natural ambient audio秒级，可重跑
T4 关键帧code(GPU)prompt_cnframes/NN.png + 拼图关键帧齐 + 一屏可审10 s/张重出
T5 分段镜头code(GPU)shots.json + cast/clips/NN.mp45.17 s / 640×352 / 有音轨 / 非黑帧单镜重试 ≤3 且换 seed；标 redo
T5 审片人（agent 代看）成片抽帧review.md（35 镜结论）+ review.json通过 / 重出 / 改词 全部有结论「重出」= 删 clip，下次只重出该镜
T5 证据表codeclips/ + frames/qc/evidence.md给出"先看这 N 镜"排序无图环境的评审入口
T6 整集code(CPU)clips/episode.mp4 + subtitles.srt/.ass规格 + 响度 + 字幕可见只重出问题镜
T7 质检code成片 + 源镜report.json阻断 = 0按 where 指回具体镜
T8 交付审批人报告 + 审片单 + 证据表 + 交付件approval.json + logs/approval.log批准时客观门禁全过驳回（必须写理由/镜号）→ changes_requested

3.3 人在环的三个决策点

1
挑定妆图 —— 角色锚点是全剧一致性的天花板。主图 = 脸最正、五官无遮挡；备图 = 同一张脸、角度略不同（给 ref2va 一点变化余地）。
2
逐镜审片 —— 每镜一个结论：通过 / 重出 / 改词。判据必须是成片抽帧，关键帧不能代表成片（实测：按关键帧误判 29 镜，真缺陷只有 7 镜）。
3
交付审批 —— 这一集批不批。批准时客观门禁重跑；驳回必须写理由；批准后成片再被改动 → 批准自动失效。

3.4 一集的时间线（实测）

阶段耗时期间人在干什么
剧本 + 台词5–10 min（LLM，CPU/GPU 间歇）等；可同时写下一集
定妆图（全剧一次）70 s挑图
关键帧≈ 6 min（35 镜 × 10 s）审关键帧拼图，标记要改的镜
出镜≈ 2.0 h（35 镜 × 170–210 s）不用守着（心跳+看板看着）
审成片5–10 min逐镜判定
后期 + 质检≈ 2.5 min等
审批 + 出包≈ 2 min签核

墙钟合计 ≈ 2.5 h/集（GPU 约 95%）。竖屏版需再渲一遍（同规格）。

4 · 功能设计

4.1 任务看板

一集 = 13 张卡片。卡片状态 = 产物在不在，不由流水线自报。

卡片状态判据显示
T1 剧本预检story.json 存在已就位 / 还没有剧本
T0 写剧本同上（manual：看板不代跑，需要题材参数）需要题材一句话
T2 台词/字幕有字幕的镜 ≥ 40%字幕 30/35
T3 定妆候选图cast/*_cand*.png 存在候选 9 张
T3 挑图落地每角色有 cast/<id>.png已选 2/2
T4 分镜shots.json 存在35 镜
T4 关键帧frames/ 数量 ≥ 镜数关键帧 35/35
T5 分段镜头clips/ 数量 ≥ 镜数镜头 35/35
T5 审片review.json 全部有结论且无 redo已审 35/35 · 待重出 0
T5 证据表qc/evidence.md 存在已生成 / 还没跑
T6 整集episode.mp4 存在132 MB
T7 质检report.json 存在且阻断 0阻断 0 · 字幕 32/35
T8 交付审批approval.json 状态已批准 / 已提交待批 / 已驳回待改 / 待提交
触发语义。点「运行」→ 后端起子进程 → 写 logs/stage-<key>.pid 与 logs/stage-<key>.log → 看板读这两个文件显示"运行中"与心跳尾。 同一阶段重复触发会被拒（pid 还活着）。「停止」杀整个进程组（渲染会起子进程）。

4.2 审片台（六个页签）

页签目的关键元素写操作
分镜审片逐镜判定每镜：视频/关键帧、字幕、角色、通过/重出、备注review.json；「重出」= 删该镜 clip
定妆选图挑主图/备图候选缩略图（已选高亮）cast/selection.json
放映整剧连看海报墙（封面+集名+时长+质检状态）、页内播放、连续播放无（只读）
交付审批这一集批不批状态徽标、决议人、理由、提交/批准/驳回、决议历史approval.json + logs/approval.log
任务看板看进度 / 触发13 张卡片、运行/停止、执行者下拉（cli / agent）起进程
成片与质检看结果播放器、findings 表、agent 日志尾无

权限：读操作局域网开放（自己的片子自己看）；写操作必须带令牌（URL ?k=… 或 X-Studio-Token 头）——因为「重出」会删 clip、「驳回」会改决议。

4.3 交付审批层

pending─submit→submitted─approve→approved 　│changes_requested─submit→submitted
三条硬规则
  1. 批准时重跑客观门禁（不信提交时的快照）：质检阻断 / 逐镜审片（未通过 + 未填）/ 证据表 / 交付件齐全 / 字幕覆盖 —— 任一不过，批准被拒并写明是哪一项。
  2. 驳回必须给理由或镜号，否则拒绝执行。
  3. 批准会自己失效：批准后成片或 clip 被改动 → 状态自动回落 pending（logs/approval.log 留 auto-reset 一行）。

4.4 证据表（无图环境的取证层）

给「只能 SSH、只有 TUI、看不到图和视频」的场景。每镜 4 个客观事实 + 旗标 + 排序：

事实怎么测能暴露什么
亮度 / 饱和signalstats过暗、过曝、与上一镜亮度跳变（观众立刻感觉到）
静止秒数freezedetect卡住 / 废镜
关键帧 vs 成片 PSNRpsnr filter哪条证据路径不可信（PSNR 低 = 关键帧不能代表成片）
与上一镜相似度8×8 彩色签名重复镜

产出 qc/evidence.md：一张表 + 「先看这 N 镜（按优先级）」。评审从"全片扫"变成"看 5–10 镜 + 抽 3 镜"。

4.5 上传包（发布交接）

不自动发布（账号/实名/风控不进脚本），而是把材料备齐并自检，人在平台后台粘贴。

包内文件内容
episode.mp4竖屏主交付（硬链接，不占额外空间）
cover_*.jpg封面
release_meta.json标题/简介/标签/时长/分辨率（从成片实测，不手填）
subtitles.srt平台自带字幕轨用（画面里已烧一份）
文案.txt可直接粘贴的标题 / 简介 / 话题标签
CHECKS.md上传前最后一道客观闸门：阻断项、字幕覆盖、响度/峰值/LRA、人工审片未通过与未填数、文件 sha256、上传步骤
CHECKS.md 会当场抓出两类"文件齐全但不能发"的假交付： ① 审片单是空模板（结论列是未勾选的复选框 = 没人判过）； ② 质检报告是中途态（如"缺镜头"阻断）。这两类只有自检表看得出来。

5.3 交互细则

  • 「重出」是破坏性动作：会删掉该镜 clip。因此必须带令牌，且在 UI 上与「通过」区分颜色。
  • 自动刷新：默认 5 秒一轮（可关）。刷新只更新投影，不打断正在播放的视频。
  • 错误提示要说人话：例如"客观门禁未过，不能批准：人工逐镜审片（35 镜：未通过 0，未填 35）"，而不是 HTTP 403。
  • 长任务的反馈：阶段卡下方显示该阶段日志的最后 2 行（心跳），让人知道"在动"而不是"卡住"。
  • 不可逆动作留痕：审批决议写 approval.json + 追加 logs/approval.log（只增不改）。

7.2 可靠性

  • 幂等：所有阶段可重复执行；中间件按 mtime 判断是否需要重做（改字幕不必重拼重放大）。
  • 断点续跑：渲染粒度 = 单镜；崩在第 34 镜不重跑前 33 镜。
  • 失败不破坏既有产物：装配失败保留旧成片；渲染失败只标 redo，不删其它镜。
  • 状态自愈：成片/clip 在批准后被改动 → 批准自动回落 pending。
  • 服务自愈：审片台 systemd Restart=always，崩溃 5 秒后拉起（实测）。

7.3 可复现

  • 每镜 seed 固定并记录在 clips/manifest.json；成片只用可复现档（缓存档只用于草稿）。
  • 组件版本钉在 platform.lock.json，由 ops/relock.sh 刷新（禁止手抄）。
  • 平台总控、web 平台、剧集产物三个仓库各自独立 git 历史，互不牵制。

7.4 资源纪律

单卡 22GB 是唯一硬瓶颈。本地 LLM 常驻 13–19GB，H3 渲染/超分需 ≈20GB → 两者不能共存。 所有 GPU 动作前必须确认显存 < 4000 MiB（superres.py 自带 wait_gpu 门控）。 渲染期间温度实测可达 86°C（阈值 85°C）→ 长时间连渲后要停机降温。

7.5 安全

面策略
写操作（删 clip、改决议、起进程）必须带令牌；令牌固定存 ~/.config/shortdrama/studio.token（600），不入库
读操作（看片）局域网开放；对外分享用静态资产页（只读、无令牌）
绑定地址默认 127.0.0.1；开放局域网需显式 --host 0.0.0.0
凭据auth.json / gh/hosts.yml / token 一律不入库（.gitignore 已钉）
渲染体ComfyUI 无鉴权（C7 风险）→ 生产建议绑 127.0.0.1 或 tailscale

8.1 交付门禁（五类，一条命令）

客观门禁保证"不难看、不断片、规格对"，保证不了"好看"。节奏感、情绪、演员感必须由真人判断： ① 拉同题材爆款做分镜拆解表，逐行比；② 找真人剪辑/导演看成片，只问三句"哪镜出戏、哪句假、结尾想点下一集吗"； ③ 5–10 个目标受众盲测，二选一而不是打分（人对打分客气，对二选一不会）。

9 · 已知限制与路线

9.1 当前限制（如实记录）

限制事实影响最便宜的改法
清晰度的天花板H3 原生只出 640×352，交付是 3× 插值；真超分（ESRGAN 4×）实测 1.9 s/帧 → 2.2 h/集，且与 LLM 抢显存会 OOM画面仍偏软（锐化后 1.45×）① 停 LLM 换窗口跑超分；② 提高原生渲染分辨率重渲（~23 h GPU）
配音是外挂 TTS单音色/每角色一音色，非真人；情绪靠字幕与镜头语言专业评审会判低分真人配音或情绪 TTS（另立项目）
画面内的字是模型写的个别不通顺；霓虹招牌汉字是乱码发布级风险（观众当真线索）提示词写"no readable writing"；关键道具后期贴真字
否定约束失效扩散模型不执行"没有人"这类约束（E03 s15 仍有远景人影）单个镜头穿帮改成纯正向描述后重渲该镜（210 s）
竖屏关键帧仍是横图关键帧阶段未按竖幅出图不能当 i2v 首帧关键帧生成按 aspect 分支
逻辑体检依赖本地 LLMLLM 未启动时只能人工过漏检LLM 与渲染互斥 → 排窗口
