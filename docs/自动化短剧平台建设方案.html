自动化短剧 / 短视频平台 · 建设方案

目标机器：X99 · 双路 Xeon E5-2680 v4（56 线程）· 32GB RAM · RTX 2080 Ti 22GB（sm_75）· 1TB NVMe

技术底座：pi-agent（编排/Agent） + ComfyUI v0.33.1 + MiniMax-H3 W4A8（渲染） + 本地 LLM（剧本），模型全部本地化

本方案只做「一件事」：一句话题材 → 本地出成片。全部数字标注可信度：【实测】/【推算】。

0 · 一页速览

如果只读一节，读这节。

166–198 s单镜 5.2 秒成片耗时【实测】
≈ 40 min一集 60 秒短剧 GPU 占用【推算】
8.3 s中文定妆图出图【实测】
r = 0.998跨镜人物一致性【实测】
1 张可并行渲染的 GPU（22GB 独占）

0.1 方案一句话

用 pi-agent 做"编剧 + 调度 + 质检"，用 ComfyUI + MiniMax-H3 做"画 + 拍"，用本地 27B LLM 做"写"，用 ffmpeg 做"剪"，中间用一份 JSON 契约串起来。 整条链路的每一个零件本机都已经跑通过（剧本除外），本方案要做的不是"从零搭平台"，而是把已经跑通的六块零件按一条流水线接起来，并补上缺失的那一块（剧本生成 + 编排调度）。

0.2 六个阶段（每段都有现成资产可复用）

题材→ P1 剧本 本地 LLM→ story.json→ P2 定妆图 Z-Image→ cast/*.png→ P3 分镜 LLM→ shots.json→ P4 出镜 H3 W4A8→ clips/*.mp4→ P5 后期 ffmpeg→ episode.mp4→ P6 质检

0.3 三句话风险

① 单卡显存是唯一硬瓶颈。本地 LLM（13–17GB）和 H3（≈20GB）不能同时驻留，所以整条流水线必须阶段串行，不能像云上那样"边写剧本边渲染"。
② 缓存加速档不可复现。T8 / FirstBlockCache / TeaCache 命中会 fork 采样轨迹，同 seed 出不同画面。→ 草稿用缓存档，成片用 bypass 档（h3turing.tiers.reproducible_only() 已经把这条纪律写进代码）。
③ H3 的原生音轨与 latent 帧数绑定。插帧能变流畅但不会延长声音；台词配音首版不本地化，靠字幕 + 原生环境音顶。

0.4 不做什么（明确划界）

  • 不做 Web 后台 / 多租户 / 数据库。交付形态 = 一个 CLI + 一个任务目录 + pi-agent 里的一条 skill。理由：单机单人产线，YAGNI。
  • 不做本地 TTS 训练或微调。首版台词走字幕；TTS 排在 P2（见 §12 里程碑 M6）。
  • 不做角色 LoRA 训练。一致性靠"同一张参考图反复喂入"（ref2va 路线，已实测 r=0.998）。
  • 不引入新的视频底模（Wan / Hunyuan / CogVideoX 等）。本机只在 H3 上验证过加速路线，换底模等于从头踩坑。
  • 不做自动发布（抖/快/视频号）。出片到 MP4 为止。

3 · 硬约束与红线

这些是物理事实和已踩过的坑，方案里任何设计都不能违反它们。

约束事实对设计的强制要求
C1 · sm_75 无 BF16/FP8 张量核Turing 张量核只支持 FP16/INT8；BF16 是模拟实现（慢约 7 倍）视频一律 W4A8（量化误差 0.0110；W4A4 是 0.2005，18 倍且彩色撕裂 → 永久排除）；出图一律 int8 存储 + fp16 计算
C2 · 单卡 22GB 显存H3 出片时占用 ≈20GB；本地 27B LLM 需 13–17GB两者不能共存 → 全流程阶段串行 + 显存门控（见 §10）
C3 · 32GB 内存模型加载峰值 + ffmpeg + LLM 上下文同驻会 OOM同一时刻只加载一个重模型；大文件下载/解压避开渲染时段
C4 · H3 音画帧数绑定181 帧 → 音轨 8.0s；121 帧 → 5.2s；插帧只扩画面不扩声需要更长音轨的镜头必须原生生成足够帧数；RIFE 只能用于"同长度提流畅度"（124→247@48fps）
C5 · 缓存档不可复现T8/FBC/TeaCache 命中会 fork 采样轨迹，同 seed 出不同画面成片档只允许 tiers.reproducible_only()；缓存档仅用于草稿
C6 · T8 默认参数是负优化阈值 0.12 在 4 步路线命中 0/4，纯加 175MB 开销缓存阈值固定用 1.0（4 步路线）／0.60（FirstBlockCache 路线），不开放给用户乱调
C7 · ComfyUI 无鉴权监听 0.0.0.0 时同网段任何人可提交任务、读 output生产模式改绑 127.0.0.1 或 tailscale 地址 100.69.133.37；对外只开只读静态服务
C8 · 冷启动 40–60s模型首次驻留显存要 40–60 秒，热运行后每镜才是 166–198s计时口径要分开报"冷/热"；批量作业先投一镜预热再计时
C9 · prompt_id 静默去重同输入重提会被静默去重（A/B 实验会"消失"）每次改参数必改 seed（bump_seed()），或带唯一 client_id
C10 · 显存被打爆会黑屏TDR / OOM 黑屏；长片（15s+）需 --reserve-vram 4渲染参数固定化：--reserve-vram 2.5 --vram-headroom 0.5 --disable-pinned-memory；≥15s 片段改 4

4 · 总体架构

4.1 分层图

人（选题/审片）→ pi-agent 编排层→ 任务队列/状态机→ LLM 层→ 渲染层 ComfyUI→ 后期层 ffmpeg→ 质检层→ 成片
层职责实现GPU
编排层把"一句话"翻译成一串阶段任务；驱动 LLM、监控渲染、汇总报告pi-agent（skill + pi --print / --mode json 无头调用）无
调度层任务目录 / 状态机 / 断点续跑 / 显存门控 / 重试新写：sd CLI（文件型 job 目录，不引数据库）无
LLM 层剧本、分镜、台词、字幕抽象层 llm.py：本地 llama.cpp :8080 优先 → 云 API（minimax/moyu）兜底占 13–17GB，与渲染互斥
渲染层定妆图（Z-Image）、分镜控图（CN Union）、视频镜（H3 W4A8）ComfyUI :8188 + h3turing 客户端 + 现有 API 工作流占 ≈20GB
后期层拼接、字幕烧录、音量归一（−1dB limiter）、1080p 交付ffmpeg（imageio-ffmpeg 静态构建，独立 venv，不碰 ComfyUI 的 pip）无
质检层时长/分辨率/黑帧/静音/削波/缺镜检查 + 人眼抽检清单ffprobe + volumedetect + 黑帧检测无

4.2 端到端时序（一集 60 秒短剧）

阶段        组件                占用           本机实测/推算耗时
──────────────────────────────────────────────────────────────────────────────
P0 选题     人 + pi-agent        —             —（人工 1 分钟）
P1 剧本     llama.cpp :8080     GPU 13-17GB   3-8 分钟（剧本 800-1500 字）
             ↓ 阶段切换：停 llama-server，腾空显存
P2 定妆图   ComfyUI / Z-Image    GPU ≈10GB     8.3s × 3-6 张 ≈ 1 分钟
P3 分镜     llama.cpp（复用 P1 上下文）        2-5 分钟
             ↓ 阶段切换：再腾一次显存
P4 出镜     ComfyUI / H3 W4A8   GPU ≈20GB     166-198s × 12 镜 ≈ 36 分钟
P5 后期     ffmpeg (CPU 56线程)  无            1-3 分钟
P6 质检     ffprobe + 脚本      无            < 1 分钟
──────────────────────────────────────────────────────────────────────────────
合计（成片档）                                                    ≈ 45 分钟
为什么要"阶段切换"这么麻烦：这就是 C2（单卡 22GB）的直接后果。缓解手段有三条，按优先级： ① 剧本阶段一次性把 story + shots 全部生成完再进渲染（避免反复起停 LLM）； ② 本地 LLM 用 llama.cpp 时显存吃 13–17GB，可以只用 CPU 模式跑剧本（-ngl 0，但只有 1.5–2.5 tok/s，仅在短 prompt 时用）； ③ 剧本质量不达标时切云 API（minimax/moyu 已配好 key），GPU 完全空出来给渲染 —— 这是最省事的方案，代价是剧本这一步不"完全本地"。
默认策略：本地 LLM 优先，出片前保证显存干净（调度层强制门控，见 §10.2）。

6 · 十个关键决策

#决策理由 / 证据放弃了什么
D1视频底模只用 MiniMax-H3 W4A8本机唯一有实测数据 + 9 个工作流 + 加速路线（Turbo/PDD/T8/FBC/TeaCache）的底模；换底模等于重头踩 sm_75 的量化坑Wan / Hunyuan / CogVideoX 等（后述）
D2中文链路全用 Z-Image，SDXL 只做英文写实风Z-Image 8.3s、中文直出、i2i 保角色、自带 CN Union；SDXL 18s 且中文基本不认统一底模
D3人物一致性 = 同一张参考图反复喂入（ref2va），不训练角色 LoRA已有实测 r=0.998、attribution ×27.4、三镜人脸/服装一致；LoRA 训练成本与调参量远超收益角色 LoRA
D4成片走 bypass LoRA 档，缓存档只用于草稿bypass 166s vs merge 232s（省 29%）且同 seed 可复现；缓存命中 fork 轨迹缓存档的 40% 提速用于成片
D5阶段串行 + 显存门控，不做多任务并发C2：22GB 装不下 LLM + H3；且 ComfyUI 自身是单队列流水线并发（吞吐会翻倍）
D6剧本走本地 27B，云 API 只做兜底本机已装好、45–48 tok/s、零外网依赖；但 Q2 量化下的剧本质量要 M2 实测才知道，兜底通道必须先建好完全本地化（当前约束下不成立）
D7首版不做本地 TTS，台词用字幕 + 原生环境音本机没有任何 TTS 权重；H3 原生音频只有环境音，没有台词；引入 TTS 要单独占显存窗口且需装新模型有声短剧（首版形态：漫剧 / 动态漫）

D9交付形态 = CLI + 任务目录，不做 Web 后台单人单机产线；pi-agent 的 TUI 已经能当"操作界面"Web 控制台、账号体系
D101080p 交付用重采样，不用 ML 超分本机无放大模型权重，nvidia-vfx 需 TensorRT 装不上，静态 ffmpeg 无 CUDA 滤镜真超分清晰度

8.4 状态机

PENDING → STORY → CAST → SHOTS → RENDER → ASSEMBLE → QC → DONE
                        ↑___________ 任意一步失败 → RETRY(≤3) → FAILED
RENDER 内部逐镜：shot_01 … shot_12，每镜独立记录状态（断点续跑粒度 = 单镜）
断点续跑粒度做到单镜是刻意的：单镜 166–198s，一集 12 镜 36 分钟，崩在第 11 镜不该重跑前 10 镜。

9 · 流水线六阶段细则

9.1 P1 剧本

项内容
输入题材一句话 + 风格 + 时长 + 镜头数
做法提示词模板 → 本地 LLM → 结构化 JSON；schema 校验失败则带错误信息重试（≤2 次）；仍失败 → 云 API
产出story.json（§8.1）
验收镜头数与时长吻合（12 镜 × 5.2s ≈ 60s）；每镜有 prompt_en + subtitle_cn；角色描述非空
风险Q2 量化的 27B 可能写出冗长散文或镜头数漂移 → 模板里强制输出 JSON + 镜头数上限，代码做二次裁剪

9.2 P2 定妆图（角色锚点）

项内容
输入story.json 的角色描述
做法Z-Image t2i（中文提示词） 生成候选 2–4 张 → 按一致性挑 1 张为主参考 + 1 张备选 → 后续分镜用 i2i（denoise 0.6–0.75） 派生变体，保持同一张脸
产出cast/c1.png（主）、cast/c1_alt.png（备选，供 ref2va 的 <Picture 2>）
验收主参考图脸型/服装可辨、可复用于全剧；参考图必须在渲染前 upload 到 ComfyUI input/（shortvideo.py 已有 upload_image()）
关键点定妆图质量 = 全剧人物一致性的天花板。这一步多花 2 分钟挑图，胜过重拍 10 镜

9.3 P3 分镜

项内容
输入story.json + 参考图清单
做法LLM 把每镜翻成 H3 风格的英文提示词：<Picture 1> shows the same character. 动作 + 镜头运动 + 光线 + 风格 + natural ambient audio: …
产出shots.json（§8.2，格式与现有脚本一致）
验收每条含 <Picture 1> 引用；含 natural ambient audio 描述（否则该镜没声音）；镜头顺序与剧本 beat 一致
提示词纪律沿用现有已验证句式（<Picture 1> and <Picture 2> show the same character. …, cinematic …, natural ambient audio: …）——这是实测出片的句式，不要让 LLM 自由发挥结构

9.4 P4 出镜（渲染）

项内容
输入shots.json + cast/
做法逐镜：套 i2v-final（或 i2v-rife）模板 → 替换 __H3_PROMPT__ / __H3_REF_IMAGE_1__ → POST /prompt → 轮询 /history/{pid} → 下载产物 → 落盘 clips/NN.mp4
产出clips/*.mp4（每镜 640×352 / 24fps / 带音轨）
纪律① seed 每镜递增（避免 prompt_id 静默去重 C9）；② 成片只允许 reproducible_only() 档；③ 单镜失败重试 ≤3 且每次换 seed
验收每镜：时长 ≈ 5.2s、分辨率 640×352、有音轨、非黑帧

9.5 P5 后期合成

步骤做法参数
① 拼接concat demuxer 逐样本 copy（音轨不重编码）-c copy，要求各镜参数完全一致
② 字幕story.json 的 subtitle_cn → SRT → 烧录思源黑体 / 白字黑边 / 底部安全区
③ 音量统一响度 + 限幅−1dB limiter（H3 音轨实测 mean −14~−34dB，缓存档低 8dB，务必归一）
④ 交付分辨率upscale_video.py --scale 3：640×352 → 1920×1056音轨逐样本不变
⑤ 输出H.264 + AAC，24fpsepisode.mp4

9.6 P6 自动质检

检查项方法不通过怎么办
时长ffprobe 读时长，与 story 目标差 > 0.5s告警（可能是某镜帧数不对）
分辨率/帧率1920×1056 / 24fps阻断
黑帧blackdetect标记该镜，重出
静音silencedetect（H3 无音轨时）标记该镜
削波volumedetect max > −0.3 dB重挂 limiter
缺镜镜头数 vs story阻断
人眼抽检生成 contact sheet（每镜抽 1 帧 + 定妆图并排）人工确认一致性

10.2 显存门控（gate.py）规则

  1. 渲染前置条件：nvidia-smi --query-gpu=memory.used < 2000 MiB（ComfyUI 模型已卸载）且 无其它 LLM 进程（pgrep -f llama-server 为空）。
  2. LLM 前置条件：ComfyUI 队列为空（GET /queue 返回空），且显存占用 < 4000 MiB。
  3. 超时：门控等 300s 超时则报"显存被占"，并打印占用进程，不自动杀进程（避免杀掉正在出的成片）。
  4. 安全阈值：H3 需要 ≈20GB，--reserve-vram 2.5 已为显示与驱动留余量；因此渲染期间严禁启动任何 LLM。

10.3 断点续跑与幂等

层级续跑粒度实现
阶段级P1…P6 任一阶段job.json 的 stage 字段
单镜级12 镜中的任一镜clips/NN.mp4 存在 + 质检通过则跳过
幂等键（story 摘要 + tier + seed + 参考图 hash）键变了才重出，避免"改了字幕就重拍全片"

10.4 单机 vs 未来多机

本方案按单机单卡设计。要扩到多机时，只需改两处：① config.py 里 ComfyUI/LLM 的 base URL；② 调度层加"选哪台机器"的路由。渲染层、剧本层、后期层代码不动。这是刻意留的扩展缝，但现在不实现。
