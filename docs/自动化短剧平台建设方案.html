自动化短剧 / 短视频平台 · 建设方案

目标机器：X99 · 双路 Xeon E5-2680 v4（56 线程）· 32GB RAM · RTX 2080 Ti 22GB（sm_75）· 1TB NVMe

技术底座：pi-agent（编排/Agent） + ComfyUI v0.33.1 + MiniMax-H3 W4A8（渲染） + 本地 LLM（剧本），模型全部本地化

本方案只做「一件事」：一句话题材 → 本地出成片。全部数字标注可信度：【实测】/【推算】。

v2 修订（2026-11-04）：按 D202611_001 三集实跑（横屏 3 + 竖屏 3，共 105 镜）反馈修订；形态从「CLI + 任务目录」升级为 Web 模式——pi-agent 作为 agent 内核，浏览器里管「任务 → 剧本 → 台词 → 人物/场景图 → 分段镜头 → 整集」全链路。修订点：§4.3–4.4 · D18–D21 · §15.7 实测数据。

如果只读一节，读这节。

0.1 方案一句话

用 pi-agent 做"编剧 + 调度 + 质检"，用 ComfyUI + MiniMax-H3 做"画 + 拍"，用本地 27B LLM 做"写"，用 ffmpeg 做"剪"，中间用一份 JSON 契约串起来。 整条链路的每一个零件本机都已经跑通过（剧本除外），本方案要做的不是"从零搭平台"，而是把已经跑通的六块零件按一条流水线接起来，并补上缺失的那一块（剧本生成 + 编排调度）。

0.2 全链路：任务 → 剧本 → 台词 → 人物/场景图 → 分段镜头 → 整集

Web 建任务→ P1 剧本 agent+LLM→ story.json→ P2 台词/字幕 agent+LLM→ dialogue_cn→ P3 人物/场景图 Z-Image→ cast/*.png→ P4 分镜+关键帧 Z-Image→ shots.json + frames/*.png→ P5 分段镜头 H3 W4A8→ clips/*.mp4→ P6 整集 ffmpeg→ episode.mp4→ P7 质检

每一格 = Web 上的一张阶段任务卡（§4.4）：点一下 → pi-agent 内核接单 → 产物落回 job 目录 → 网页投影刷新。全链路没有数据库、没有第二份状态（D11 / D18）。

0.3 四句话风险

① 单卡显存是唯一硬瓶颈。本地 LLM（13–17GB）和 H3（≈20GB）不能同时驻留，所以整条流水线必须阶段串行，不能像云上那样"边写剧本边渲染"。
② 缓存加速档不可复现。T8 / FirstBlockCache / TeaCache 命中会 fork 采样轨迹，同 seed 出不同画面。→ 草稿用缓存档，成片用 bypass 档（h3turing.tiers.reproducible_only() 已经把这条纪律写进代码）。
③ H3 的原生音轨与 latent 帧数绑定。插帧能变流畅但不会延长声音；台词配音首版不本地化，靠字幕 + 原生环境音顶。
④ 一集渲染 ≈ 2 小时的黑箱等待（v2 新增）。35 镜 × 170–210s【实测】。没有 Web 看板 + 心跳日志时，人只能对着一个黑着的终端等——这正是把形态改成 Web 模式的直接原因（D18）。

0.4 不做什么（明确划界）

  • 不做多租户 / 账号体系 / 数据库（v2 修订）。Web 模式只做两件事：任务看板（管全链路）+ 审片台（管人的决定）；状态仍以 job 目录文件为唯一真相源，网页只是投影 + 触发器（D11 的延续，见 D18）。
  • 不做本地 TTS 训练或微调。首版台词走字幕；TTS 排在 P2（见 §12 里程碑 M6）。
  • 不做角色 LoRA 训练。一致性靠"同一张参考图反复喂入"（ref2va 路线，已实测 r=0.998）。
  • 不引入新的视频底模（Wan / Hunyuan / CogVideoX 等）。本机只在 H3 上验证过加速路线，换底模等于从头踩坑。
  • 不做自动发布（抖/快/视频号）。出片到 MP4 为止。

3 · 硬约束与红线

这些是物理事实和已踩过的坑，方案里任何设计都不能违反它们。

约束事实对设计的强制要求
C1 · sm_75 无 BF16/FP8 张量核Turing 张量核只支持 FP16/INT8；BF16 是模拟实现（慢约 7 倍）视频一律 W4A8（量化误差 0.0110；W4A4 是 0.2005，18 倍且彩色撕裂 → 永久排除）；出图一律 int8 存储 + fp16 计算
C2 · 单卡 22GB 显存H3 出片时占用 ≈20GB；本地 27B LLM 需 13–17GB两者不能共存 → 全流程阶段串行 + 显存门控（见 §10）
C3 · 32GB 内存模型加载峰值 + ffmpeg + LLM 上下文同驻会 OOM同一时刻只加载一个重模型；大文件下载/解压避开渲染时段
C4 · H3 音画帧数绑定181 帧 → 音轨 8.0s；121 帧 → 5.2s；插帧只扩画面不扩声需要更长音轨的镜头必须原生生成足够帧数；RIFE 只能用于"同长度提流畅度"（124→247@48fps）
C5 · 缓存档不可复现T8/FBC/TeaCache 命中会 fork 采样轨迹，同 seed 出不同画面成片档只允许 tiers.reproducible_only()；缓存档仅用于草稿
C6 · T8 默认参数是负优化阈值 0.12 在 4 步路线命中 0/4，纯加 175MB 开销缓存阈值固定用 1.0（4 步路线）／0.60（FirstBlockCache 路线），不开放给用户乱调
C7 · ComfyUI 无鉴权监听 0.0.0.0 时同网段任何人可提交任务、读 output生产模式改绑 127.0.0.1 或 tailscale 地址 100.69.133.37；对外只开只读静态服务
C8 · 冷启动 40–60s模型首次驻留显存要 40–60 秒，热运行后每镜才是 166–198s计时口径要分开报"冷/热"；批量作业先投一镜预热再计时
C9 · prompt_id 静默去重同输入重提会被静默去重（A/B 实验会"消失"）每次改参数必改 seed（bump_seed()），或带唯一 client_id
C10 · 显存被打爆会黑屏TDR / OOM 黑屏；长片（15s+）需 --reserve-vram 4渲染参数固定化：--reserve-vram 2.5 --vram-headroom 0.5 --disable-pinned-memory；≥15s 片段改 4

为什么要"阶段切换"这么麻烦：这就是 C2（单卡 22GB）的直接后果。缓解手段有三条，按优先级： ① 剧本阶段一次性把 story + shots 全部生成完再进渲染（避免反复起停 LLM）； ② 本地 LLM 用 llama.cpp 时显存吃 13–17GB，可以只用 CPU 模式跑剧本（-ngl 0，但只有 1.5–2.5 tok/s，仅在短 prompt 时用）； ③ 剧本质量不达标时切云 API（minimax/moyu 已配好 key），GPU 完全空出来给渲染 —— 这是最省事的方案，代价是剧本这一步不"完全本地"。

4.3 Web 模式：pi-agent 作为 agent 内核（v2 核心）

v1 把交付形态定为「CLI + 任务目录」。三集实跑后改判：单集 2 小时的渲染等待 + 人在环审片，让终端成了最差的操作面（pi 的 TUI 看不到图、看不到视频）。v2 改为：浏览器是唯一操作面，pi-agent 是唯一执行内核，job 目录仍是唯一真相源。

角色干什么不干什么实现
人选题、拍板（挑定妆图 / 判镜头 redo）、看成片不写命令行，不手改 JSON浏览器（PC / 手机都行）
Web 面板建任务、列阶段、显示进度与产物、写决定不执行任何 GPU / ffmpeg 动作，不存第二份状态shortdrama/studio.py（标准库 http.server；只读 GET 投影 + 带令牌 POST 写决定）
pi-agent 内核接「阶段任务卡」：读 job 目录 → 按 skill 里的纪律执行（选档位、走显存门控、判审片结论）→ 改文件 → 回写状态与心跳不引数据库，不另立状态，不越权改渲染产物pi 无头 session（pi --print --mode json）
阶段执行器确定性动作：出图 / 出镜 / 拼接 / 烧字幕 / 质检不做内容决策shortdrama/episode.py（+ tools/*.py）
为什么不让网页直接调 ComfyUI / ffmpeg：那等于把三个月踩出来的纪律（成片只用可复现档、显存门控、关键帧先行、物镜走 t2v、逐镜归一 + 两遍 loudnorm + limiter 关自动电平）用另一种语言重新实现一遍，并且立刻长出第二套状态。agent 内核 + 现有 CLI = 纪律只有一份，网页只是它的遥控器。

4.4 阶段任务卡（任务 → 剧本 → 台词 → 人物/场景图 → 分段镜头 → 整集）

D15成片响度按 EBU R128 交付：I = -16 LUFS ±1、峰值 ≤ -1.0 dBFS、LRA ≤ 12 LU短剧在手机外放播放，响度必须可预期（集与集一致才不掉完播）；LRA 20+ 的"电影感"动态范围在手机外放会忽大忽小。实现上必须两遍 loudnorm（单遍实测要 -16 只得到 -18.1，且 LRA 目标不生效）、alimiter 必须写 level=disabled（默认自动电平会把限掉的电平推回去），限幅上限压到 -2.0 dBFS（AAC 编码实测过冲 +0.5~0.6 dB：限 -1.0 → 成片 -0.6、限 -1.5 → -0.9，都超阈值阻断），attack 取 0.1ms（H3 音轨有 ~4ms 瞬态突发，attack=1ms 时突发头部样本按原电平通过 → AAC 重构越过 0 dBFS，成片出现被削平的样本：实测 E03_P 有 184 个样本顶到 1.0）响度不设标准（各集音量忽大忽小）
D14定妆图提示词 = 身份锚点 + 造型 + 中性光后缀；风格词不进① 风格词（霓虹洋红 / 低照度 / 胶片颗粒）会覆盖"中性柔光、纯灰背景"，模型顺势出美颜网红脸，且带色光污染 ref2va 参考图；② 不给性别 / 年龄 / 人种，Z-Image 默认出男性（实测三个角色全出成男的）→ 身份锚点独立成字段并硬性校验好看的通用定妆照（但锁不住人脸）

9.1 P1 剧本

项内容
输入题材一句话 + 风格 + 时长 + 镜头数（35 镜 × 5.17s ≈ 181s/集）
做法提示词模板 → 本地 LLM → 结构化 JSON；schema 校验失败则带错误信息重试（≤2 次）；仍失败 → 云 API。分块写：一次写 12 镜（超过就被 max_tokens 截断，实测 E01 第一次就截断过）；LLM 开着 reasoning，token 预算要给足
产出story.json（§8.1）
验收lint 无 block：prompt_en 非空且无中文、idx 连续 1..N、ref 角色存在、duration_s ≈ 5.2；每镜有 prompt_cn（关键帧要靠它出图）
风险Q2 量化的 27B 可能写出冗长散文或镜头数漂移 → 模板强制 JSON + 镜头数上限，代码二次裁剪

9.2 P2 台词 / 字幕（v2 新增阶段：主信息通道）

项内容
为什么单列实跑：初版 3 集共 105 镜，对白只有 2 / 7 / 7 条。剧本是纯动作流 → 观众三分钟几乎读不到信息。短剧是听觉媒介，台词/旁白是主信息通道，不是装饰
输入story.json（每镜 beat / 在场角色 / 已有字幕）
做法代码决定哪些镜该有台词（钩子镜与尾钩镜不写——用画面说话；有人在场必写；物镜按 beat 判）+ LLM 只负责写内容（每句 ≤16 字、不解释不抒情、不剧透、不许留空）→ 合并进 story.json（已有字幕不动）
产出每镜 dialogue_cn / subtitle_cn；只改文本，不改镜头 → 不需要重渲，只需重跑 assemble
验收有效字幕覆盖率 ≥ 40%；有效字幕与台词分开算，两者都 <15% 才告警（悬疑片台词天然少，但两个都低就是信息断链）
风险第一版把"选镜"也交给 LLM → 它理解成"沉默也是戏"，35 镜只写出 1 条，还覆盖掉已有的好字幕（靠 git checkout 才救回来）。教训：选镜权在代码、写入是合并不是覆盖

9.3 P3 人物 / 场景图（角色锚点）

项内容
输入story.json 的角色描述（身份锚点 + 造型 + traits_en 英文特征词）
做法Z-Image t2i（中文提示词） 出候选 2–4 张（约 10s/张）→ 审片台挑 1 张主参考 + 1 张备选（i2i 派生）→ 后续镜用 ref2va（<Picture 1> 主 + <Picture 2> 备）
产出cast/<id>.png（主）、cast/<id>_alt.png（备）。全剧共用（cast/ 软链到剧集根）→ 跨集不换脸

9.4 P4 分镜 + 关键帧（关键帧先行）

项内容
输入story.json + 参考图清单
做法① shots.json：H3 固定句式（<Picture 1> and <Picture 2> show the same character. …, <style>, natural ambient audio: …），不让 LLM 自由发挥结构；② 关键帧：每镜 1 张 Z-Image 图（约 10s/镜）→ frames/NN.png + qc/keyframes_sheet.png 拼图
产出shots.json（含 subtitle_cn / dialogue_cn，供 SRT 与质检用）+ frames/
验收每条含 ref 声明（null = 物镜，走纯 t2v，D13）；含 natural ambient audio；关键帧拼图一屏审片
为什么关键帧先行构图/人物/光线对不对，用一张 10s 的图就能判断，用视频要 210s——审片成本差 20 倍（D20）。审图在烧 GPU 之前，改图比重渲便宜两个数量级
文字纪律画面里不得出现需要观众读懂的文字（D12）：H3 / Z-Image 画出的字必是乱码。可读信息一律进 subtitle_cn（后期烧，一定正确）

9.5 P5 分段镜头（渲染）

项内容
输入shots.json + cast/
做法逐镜：套 i2v-final（人物镜）/ t2v-final（物镜）→ 替换 __H3_PROMPT__ / __H3_REF_IMAGE_1__ → POST /prompt → 轮询 /history/{pid} → 下载 → clips/NN.mp4

实测170–210 s/镜（ref2va 为主）；35 镜一集 ≈ 1 小时 55 分；竖屏同规格再渲一遍
纪律① seed 每镜递增（避免 prompt_id 静默去重 C9）；② 成片只允许 reproducible_only() 档；③ 单镜失败重试 ≤3 且换 seed；④ 角色 traits_en 英文特征词进提示词（R17：只靠参考图会漂，实测 9 镜把人渲成年轻男性）
验收每镜：时长 ≈ 5.17s、640×352、有音轨、非黑帧；重出只重出该镜（删 clip 即可续跑）

9.6 P6 整集（后期合成）

步骤做法参数 / 实测
① 逐镜归一每镜先对齐到同一响度，再拼（整片归一会把动态压扁）loudnorm=I=-20:TP=-3:LRA=11；实测整片 LRA 20.8 → 7.4 LU
② 拼接concat demuxer，-c copy横屏 3× 上采样到 1920×1056；竖屏直接 scale 到 1080×1920
③ 烧字幕libass + Noto Sans CJK SC，白字黑边横屏 FontSize=42,MarginV=56；竖屏 FontSize=54,MarginV=360（避开平台 UI）。只去相邻重复，隔得远的重复是叙事回环保留
④ BGM 情绪床assets/bgm.oga（CC BY 4.0，署名随片）垫底amix normalize=0 + 必须走 -filter_complex（-af 是单输入链，装不下第二路；实测踩过）
⑤ 整片响度两遍 loudnorm + 限幅alimiter level=disabled（默认自动电平会把限掉的电平推回去 → 数字削波）。实测 I=-16.0 LUFS、峰值 -1.1 dBFS
⑥ 系列级亮度测整片平均亮度 → eq 校正到 YAVG 90实测 E01 94.6 / E02 100.6 / E03 82.0 → 统一到 88.5–90
⑦ 输出H.264 + AAC 24fps + faststartepisode.mp4（横屏 1920×1056 / 竖屏 1080×1920）
中间件复用：concat / upscaled / norm 都带"比依赖新就跳过"的判断（_fresh()）——只改字幕时，重跑 assemble 只需重烧字幕，不必重拼重放大（实跑 3 集 assemble ≈ 1.5 分钟）。

10.2 显存门控（gate.py）规则

  1. 渲染前置条件：nvidia-smi --query-gpu=memory.used < 2000 MiB（ComfyUI 模型已卸载）且 无其它 LLM 进程（pgrep -f llama-server 为空）。
